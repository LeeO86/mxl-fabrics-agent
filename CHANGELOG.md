# Changelog

## 1.7.3

- Audio passes every 2 ms again, as in 1.7.1 (`AUDIO_PASS_MS`, new, 1 to 20, default 2). 1.7.2 was rolled back on the platform after 14 min: over RoCE (E810, irdma) the gateway's audio read timeouts rose from 1530 to 8111 per 10 min and FlowXer's missing audio from 222 to 570. `sample_transfer_max_seconds` showed 0.53–0.55 s while irdma's `RetransSegs` rose by one or two per host in 30 s and nothing else moved (no RNR, no thread stalls, delivered sample age 17–40 ms). One audio transfer is in flight per flow, and each lost RoCE packet holds that flow until the sender's retransmit timer runs out, about half a second there. 1.7.2's 1 ms audio pass sent about 30 % more, smaller transfers, so more of them were lost. The pass interval is now also the least time from the pass that saw a transfer complete to the next one, never under 2 ms. Lab (`tcp`, two agents, four 2 ch 48 kHz flows with 1 ms commits and a 1080p50 flow, 30 s): 239 transfers a second per audio flow (1.7.1: 241; 1.7.2 and `AUDIO_PASS_MS=1`: 312), so one thread per flow sends no more than 1.7.1's one thread per domain at the same interval; agent CPU about 8 % above 1.7.1 (1.7.2: 15 to 19 %). The sync batch limit is unchanged.
- The ACK timeout and retry count of the `verbs` queue pairs can be set: `FABRIC_ACK_TIMEOUT` (new, the exponent n of 4.096 µs × 2^n, 4 to 24, default 14 = 67 ms; 0 leaves rdma_cm's 17 = 537 ms of up to 1.7.2) and `FABRIC_RETRY_COUNT` (new, 1 to 7, default 7 as before). libfabric 2.3.1's `verbs` provider has no setting for either (it sends retry count 15, which the kernel takes as 7, and never sets the timeout), and MXL 218ddaa does not expose its endpoints. The agent binary now defines `rdma_connect`, `rdma_accept`, `rdma_get_cm_event` and `rdma_destroy_id` itself (exported; the dynamic linker binds libfabric's calls to them, checked with `LD_DEBUG=bindings`) and calls librdmacm's behind them. Before a connect or accept it sets `RDMA_OPTION_ID_ACK_TIMEOUT` on the rdma_cm id, and the connect carries the retry count; when the connection is established it reads both back from the queue pair (`ibv_query_qp`). LD_PRELOAD would not work, because the image's binary has file capabilities.
  - Effective on NICs that honour the QP timeout (mlx5, rxe). On E810 with the in-tree or Intel's irdma (2.6.96 on the platform) the timeout is ignored: the retransmit timer is the device's `roce_rtomin`, and `ibv_query_qp` reports no timeout. The retry count applies.
  - Log `fabric_qp` per queue pair, at both ends: `role`, `flow_id`, `peer`, `local`, `remote`, `device`, `qp_num`, `ack_timeout` and `ack_timeout_ms` as read back (`unreported` when the driver gives none), `retry_count`, `rnr_retry`, the settings and `applied` (`warn` when they differ). `fabric_qp_settings` at start, with `rdma_cm_hooks`. Metrics `fabric_qp_established_total{role,ack_timeout,retry_count}`, `fabric_qp_option_failures_total`, `fabric_ack_timeout_seconds` and `fabric_retry_count`.
  - Not run on RDMA hardware: the lab has no RDMA device without root, and librdmacm opens no rdma_cm channel without one. Unit tests cover the order of the calls (option before connect and accept, the one-byte option, the retry count in a copy of libfabric's parameters), the read-back and its report with flow and peer, refused options, failed connects, error events and destroyed ids.
- `sample_transfer_stalls_total{provider,flow_id}` and `grain_transfer_stalls_total{provider}` (new) count the transfers longer than half the ACK timeout (`transfer_stall_threshold_seconds`, 33.6 ms with the default), most likely a retransmission, so the platform can count stalls directly. On irdma the threshold still follows `FABRIC_ACK_TIMEOUT`. Lab: three 0.3 s pauses of the destination counted 2 sample stalls per audio flow and 3 grain stalls; none without.
- `replication_late_deliveries_total` for video and data flows: late is more than two grain periods and at least 10 ms between two passes that committed grains (50p: 40 ms). 1.7.2 counted no discrete flow. For audio the usual gap is now the 98th percentile of the flow's last 256 gaps instead of a moving average. A flow whose batches come in bursts (several transfers 3 ms apart, then a longer wait for the origin's next commit) had an average well below that regular wait, and every wait counted as late (a test sequence: over 300 late in 1600 gaps with the 1.7.2 rule, none now). That is the likely cause of the platform's +514 and +185 in 30 s on two flows. A single long gap (a retransmission) still counts once. Lab: none in clean runs; with the three pauses 3 for each audio flow and for the video flow.
- README "Audio timing": the ACK timeout, which NICs use it, why each RoCE loss costs one timeout, and PFC/ECN advice.
- The deploy example uses the `1.7.3` image and sets the three settings.

## 1.7.2

- One fabric thread per flow ("lane"). Until 1.7.1 one thread (with one Fabrics instance) served every flow of a domain, and every call into it ran between two transfer passes. A slow call for one flow held up the transfers of all the others in that domain: a target or initiator set up again (picking the interface with `fi_getinfo`, registering the flow's ring, a video ring of 1 s holds about 275 MB), a writer opened or released. Lab (`tcp`, two agents, two 2 ch 48 kHz audio flows and a 1080p50 flow in one domain, 60 s): a video origin re-created every 4 s delayed the audio mirror by up to 33 ms with 1.4.1 and 40 ms with 1.7.1 (5–9 ms without it), the rebuild hook on the video mirror every 3 s by up to 38 ms with 1.7.1; with lanes the time from the origin's commit to the mirror's stayed at most 4 ms in both cases (1.7.1: up to 30 and 27 ms) and the mirror at most 14 ms behind the current time (the pattern writer itself was up to 12 ms late in those runs). Each lane has its own thread and Fabrics instance; the flows of a domain share its MXL instance as before (each MXL instance holds an inotify instance, and `fs.inotify.max_user_instances` is 128 per user by default; README "Lanes and inotify"). A lane goes when its flow has no writer, target or initiator left and nobody holds it: after each release, after a failed request and in a sweep on every reconcile pass. The check and the drop cannot lose a request that took the lane meanwhile (lane tests).
- A lane of a continuous flow makes a pass every 1 ms (discrete 2 ms, empty 50 ms). The source sees a completed transfer sooner and the destination drains sooner, so an audio transfer goes about every 3 ms instead of 4 ms (lab), and after a stall the source catches up faster (one bounce-buffer entry, 10 ms, per transfer). The gap of 2 ms between a completed transfer and the next one stays (`verbs` receive). Lab: mirror at most 6.8 ms behind (1.7.1: 9.7 ms), agent CPU about +0.07 cores for four audio flows and one video flow.
- New metrics for audio bursts, which the instant `lag_ms` misses between scrapes: `replication_sample_age_seconds{stage=origin|sent|delivered}` and `replication_sample_age_max_seconds` (largest of the last 10 s, the same for every scraper), `replication_delivery_gap_seconds`, `replication_late_deliveries_total` (gaps over twice the flow's usual gap and at least 10 ms; gaps include the origin's pauses), `sample_transfer_seconds` and `sample_transfer_max_seconds` (one audio transfer from post to completion: a transport stall), `fabric_thread_stall_seconds{task}` with the log `fabric_thread_stall`, and `reconcile_work_seconds{work}` for the periodic work (reconcile steps, the `/proc` reader scan, the peer poll, the inventory scan) with debug lines and `reconcile_work_slow` (info) over 0.5 s. The lanes count these themselves (no lock shared with a scrape, no key built per observation) and the reconcile pass copies them into the metrics. When a lane goes its final counts are kept in a running total, so series without a flow label (`grain_transfer_seconds{provider}`, which is counted the same way now, `fabric_thread_stall_seconds{task}`, and all of them with `METRICS_PER_FLOW=false`) never decrease; a per-flow series goes with its flow's lane. `flow_id` labels follow `METRICS_PER_FLOW`. README "Audio timing" explains how audio is sent and how `lag_ms` is sampled.
- Histograms can have their own buckets; the existing ones are unchanged.
- README: `RT_PRIORITY` with a narrow `CPU_AFFINITY` puts all lanes on those cores; it does not isolate them.
- The deploy example uses the `1.7.2` image.

## 1.7.1

- A target whose read fails is closed, not read again. On the platform all three agents restarted together, and about 1 s later the host-01 agent (1.6.0, `verbs`) died with SIGSEGV (exit 139) while it was accepting a peer's connection: `rdma_create_qp: Invalid argument`, then `Failed to try for new samples: Failed to accept connection ... -22`. The bug is in MXL 218ddaa (`RCTarget::readNext`, see `docs/upstream-rctarget-accept-crash.md`). When the accept path throws, the RC target keeps a moved-from state, and its next read dereferences a null event queue. The agent read the target again on the next pass (2 ms later) and crashed. Reproduced over `tcp`, in a small MXL program and in the agent, with queues that cannot be opened after the accept. Now the first read that fails is the last call into that target: the agent destroys it (log `fabric_target_closed`, `last_error` `… (target closed)`). After 1 s without a grain the destination sets up a new target on the next port and repeats the handshake; in a loop it waits 1, 2, 4 and then 8 s. In the lab (`tcp`) the new target was up 1 s after the failed accept and the mirror got grains again. Why `rdma_create_qp` failed was not reproduced (the lab has no RDMA device without root). The QP sizes are the provider's defaults for the device and the same on every accept, so the likelier cause is a connection request that the peer withdrew while it restarted. The upstream note has the details.
- The same for the source's initiator. The MXL bug is also in `RCInitiatorEndpoint::activate`: when `fi_connect` or `fi_ep_bind` throws, the next `MakeProgress` binds a null endpoint (SIGSEGV; reproduced in the agent with a refused `connect`). Now a `MakeProgress` that fails with any status other than OK, NOT_READY or INTERRUPTED closes the initiator and forgets its targets (log `fabric_initiator_closed` once per error until a pass works again; `last_error` `… (initiator closed)`). The destination's next request adds its target again, and a new initiator is opened for it. Two exceptions that MXL reports as NOT_READY or INTERRUPTED (a receive post failing with EAGAIN or EINTR right after a connection) cannot be told apart from "no data yet" and are only documented in the upstream note.
- No `origin_missing` right after a start. On the same restart host-01 logged `mirror_flow_origin_missing` for a live flow about 3 s after start, and its health showed `origin_missing` (the 30 s start guard kept it from removal). A peer's inventory now counts only when it is *settled*: the peer has been up for one full poll (two polls in a row with the same boot id) and its inventory comes from a finished scan (`revision` above 0).
  - A mirror flow that no peer lists is judged only when its domain's source peer is settled and no up peer that lists the domain is still pending. Meanwhile the health reason is `inventory_pending`, and an existing grace clock pauses, keeps its time and is not logged again. A peer restart elsewhere no longer touches it.
  - A peer that stays unsettled for longer than 60 s (or 3 poll intervals, whichever is longer) counts as down for these decisions, so a peer that fails every other poll, or restarts on every poll, holds nothing back for good. Being down in between does not reset that wait; being down for longer than the limit does, so a peer back after a long outage gets the full wait again.
  - A mirror domain is not taken for an orphan while any up peer is pending, which is likewise bounded. That domain-level case was not limited to the first 30 s after start.
  - `/api/v1/inventory` answers 503 until the agent's first scan; before, it answered an empty inventory with `revision` 0. The web UI shows "scanning" then and tries again on the next refresh. The scanner now starts before the NMOS node.
- `tests/integration/accept_fail.sh` (CI) with `libmfa-accept-fault.so` (`tests/tools/accept_fault.cpp`, `LD_PRELOAD`): the source's first connect and the destination's first accepted connection fail, and both agents have to stay up and replicate. Then both agents restart together, and no `origin_missing` may appear for the live flow. Unit tests cover a flapping peer, an unrelated peer that restarts, and the paused clock.

## 1.7.0

- A mirror whose origin came back with another flow definition is rebuilt. When a writer restarted, the destination kept its mirror flow and writer whatever the new origin looked like, so an origin that came back under the same flow id at another rate, size or format went on into a mirror with the old `flow_def.json` and layout (lab: the origin back at 25 grains/s, the mirror still said 50). Now the destination compares the origin's definition in the source's inventory with the mirror's own, ignoring the descriptive fields (`label`, `description`, `tags`, `parents`, `version`, `source_id`, `device_id`). When they differ it drops its target and the source's connection, releases its writer, removes the flow's files and creates the flow from the new definition on the same pass, readers or not (they get `MXL_ERR_FLOW_INVALID`). Log `mirror_origin_changed`, rebuild reason `origin_config_changed`, at most one per flow per 5 s. With the same definition nothing changes: the mirror stays and grains go on in the same file.
- Test hook `POST /api/v1/mirrors/{domain_id}/{flow_id}/rebuild`: rebuilds one mirror flow under the same ids (new files, new inode), so readers see `MXL_ERR_FLOW_INVALID`, then replication resumes into the new file. For testing a media function's re-open path on hardware without restarting a producer. Off unless `MIRROR_ADMIN_REBUILD=true` (new, default false, environment only and read at start, so only the deployment can open the hook: not in the config file, `PUT /api/v1/config`, the import or the export): `403` when off, `400` for ids that are not UUIDs, `404` for an unknown flow, `200` with `old_inode`, `inode` and the `readers` that mapped the old file. Logs `mirror_rebuild_requested`; the next pass logs `mirror_rebuilt` with reason `api` and counts it in `mirror_rebuilds_total`.
- README "Rebuild rules" and SPECIFICATION §7.5: when an origin restart rebuilds a mirror and when it keeps it. Lab (two agents over `tcp`, 1080p50, a receiver on the destination, the origin away 2 to 62 s): a killed writer (files left) or a clean exit (MXL deletes the flow, the domain stays) never rebuilt the mirror; a function that deletes its whole domain on exit (mxl-replay) rebuilt it every time (`mirror_domain_orphan`, already at 1.8 s away) unless a reader mapped the mirror; without a receiver a killed writer away 62 s rebuilt it (`origin_gone`); restarting the destination agent kept it.
- `mxl-pattern-writer follow <domain> <flow> <seconds>`: a reader that re-opens on `MXL_ERR_FLOW_INVALID`; `PATTERN_VIDEO_RATE` sets the video pattern's grain rate. `tests/integration/rebuild.sh` (CI): the hook's guard, a rebuild through the hook and an origin back at another rate, each with the reader reading again.

## 1.6.0

- Single mirror flows whose origin flow is gone are removed. On host-01 13 mirror flows sat in mirror domains still in use, their origin flows gone for days; 1.5.0 reported them `idle` (`origin_missing`) and the 1.4.0 cleanup only drops whole domains. ## 1.5.0

- Mirror health for the platform's re-routing. Each destination mirror flow gets a state (`live`, `pending`, `stale`, `idle`, `absent`) with a reason, the age of its newest grain and a rebuild count. `stale`: grains are due (a replication is wanted and the origin is live) but none came for `MIRROR_STALE_MS` (new, default 2000, `0` never) while the origin has newer ones or the source peer or link is down. `rebuilt`: the mirror's data file is a new one (another inode, or back after it was gone); MXL readers stay on the file they opened and see no new grain, so the platform has to activate them again. The agent only reports; choosing sources stays with the controller (IS-05).
- `GET /api/v1/mirrors`: `flows[].health` with `state`, `reason`, `last_grain_age_ms`, `stale_since`, `stale_after_ms`, `rebuilds`, `last_rebuild`, `last_rebuild_reason`. SSE event `mirror` (`stale`, `recovered`, `rebuilt`). Logs `mirror_stale`, `mirror_recovered`, `mirror_rebuilt`.
- New metrics (existing ones unchanged): `mirror_stale{domain_id,flow_id,peer}` (0/1), `mirror_state{domain_id,flow_id,peer,state}`, `mirror_last_grain_age_seconds{domain_id,flow_id,peer}`, `mirror_rebuilds_total{domain_id,flow_id,peer}`, `mirrors_stale`.
- `GET /api/v1/inventory` carries each local flow's `head_index`, read when the request is answered and not part of `revision`. A destination uses it to tell a mirror that misses grains from an origin that writes none (`idle`, `origin_silent`); with an older source the origin's `live` flag stands in.
- README: "Mirror health" with the platform contract (what to watch, when to re-route).

## 1.4.1

For audio `lag_grains` counts transfer batches and divides by the size of the last one, so a batch of one sample made 47 "grains" out of about 1 ms. `lag_grains` and `replication_lag_grains` are unchanged. ## 1.4.0

- Mirror domain cleanup. Tests and moved functions left stale destination mirrors (`/Volumes/mxl/mirror-<domain id>`) on the platform's media nodes, and the agent kept them mapped. A mirror next to its live origin (the function moved to this node) froze a reader on the platform (vmix blackout: same flow ids, stale copy). Now each mirror domain on disk gets a state: `same_node` (origin on this node) and `orphan` (no up peer lists the origin) are removed at once, `idle` (no demand) after `MIRROR_IDLE_GRACE_S` (default 300 s), `active` stays; a mirror of a local origin is never created. The agent closes its own writers and targets, then removes the flows and the directory, and only when no other process maps one of its files (`/proc/<pid>/maps`, matched by device and inode) and it could check every process; otherwise it refuses and logs `mirror_domain_busy`. Orphans are decided 30 s after start and, with NMOS, while the registry answers. `MIRROR_CLEANUP_DRY_RUN=true` only logs.
- `GET /api/v1/mirrors` lists one entry per mirror domain with origin, flows (with the per-flow state), demand, readers, `idle_since`, `age_s` and state; `DELETE /api/v1/mirrors/{domain_id}` removes one with the same checks (409 while it is mapped). Metrics `mirror_domains{state}`, `mirror_domains_removed_total{reason}`, `mirror_domains_refused_total{reason}`.
- The reader check needs the host's processes: the example DaemonSet sets `hostPID: true`, `appArmorProfile: Unconfined` (the default profile denies `ptrace read` of other processes) and adds `SYS_PTRACE`, which the image now raises from its file capabilities like `SYS_NICE`. Without them the agent removes no mirror and says why (`readers_known: false`).
- The deploy example uses the `1.4.0` image.

## 1.3.1

- Origin indexes that the writer never wrote are passed over. A writer that is late and jumps to the current grain leaves indexes unwritten (mxl-replay's playout when it is more than 2 grains late; FlowXer's next release on purpose), and MXL marks them invalid with no valid slice when the writer opens the next grain. 1.3.0 sent each of them as an empty grain: a transfer and an immediate more, back to back with the next grain, and over `verbs` MXL's target has only one receive posted for immediates (see 1.2.0). The platform's replay outputs (1080p50, 200 ms history) replicated host-03 → host-02 at 21.5 and about 0 grains/s with 2–3 restarts in 30 s, while FlowXer, late but without gaps, ran at 50.5 grains/s on the same path. Now the source skips such an index, and one whose slot holds another index or is not complete, up to the next written grain while a later one exists; the head grain is always sent, and the mirror writer marks the skipped indexes invalid in turn. `origin_gaps` in `/api/v1/replications` and `replication_origin_gaps_total{flow_id,peer}` count them. Lab (writer: 10 grains, then 3 indexes unwritten; 200 ms history; 30 s): `tcp` 38.5 good grains/s on the mirror with both versions, 1.3.0 with 1663 transfers and 1.3.1 with 1249 plus 375 gaps passed over, no error, no restart; soft-RoCE 3 "receiver not ready" with 1.3.0, none with 1.3.1 (2 grains, then 2 unwritten: 6 against none, 1664 transfers against 813). Over `tcp` 1.3.0 lost no written grain either, so the platform's `verbs` mesh is the check that counts.
- A fabric address that comes back is found again. libfabric's `verbs` provider lists its devices and addresses once, at the process's first `fi_getinfo`, and answers every later call from that list (`vrb_init_info`, `vrb_get_srcaddr_devs`, libfabric 2.3.1). On the platform networkd lost the address of two mesh ports after a link flap; agents that started without it stayed in error after `networkctl reconfigure` brought it back (destinations: "provider verbs has no interface for 192.168.250.2", the peer: `http 500`) until they were restarted. When a provider has no interface for a local fabric address that a local interface holds with carrier, the agent now builds the list again with `fi_getinfo(FI_RESCAN)` (public since libfabric 2.2; the provider swaps the list under its lock and open fabrics keep their copy), at most once per 5 s, logs `fabric_interfaces_rescanned` and tries again; the other replications go on. Lab (soft-RoCE, agent B started without its address, added 50 s later): 1.3.0 stayed at 0 grains/s both ways with those two errors; 1.3.1 rescanned 10 ms after `peer_link_up` and ran at 50.4 grains/s both ways, none missed, also after a second removal with the agents running.
- A source whose own fabric link to a destination is down answers `link_down` with the reason and sets nothing up for it (1.3.0 tried, and without the address answered a bare 500). Any other failure answers 500 with the reason in `error`, and the destination shows `http 500: <reason>`.
- `mxl-pattern-writer video … <recreate-after-s> <gap-every> <gap-length>` writes `gap-every` grains, then leaves `gap-length` indexes unwritten. `tests/integration/tcp_mesh.sh` checks such a flow (35 of 38.5 grains/s, gaps counted).

## 1.3.0

- A writer that restarts no longer stops its replications for good. MXL deletes a flow with its last writer, and a restarted writer (FlowXer, the test player) creates it again with a new inode. The source's reader stayed on the deleted flow, whose head stands still: the destination got no grain and did not rebuild, the source counted `get grain 11` (`MXL_ERR_FLOW_INVALID`) about 500 times a second (lab, re-created within milliseconds: 0 grains/s for good; with 6 s between the writers the destination released the pull and it worked). The source now checks the origin's data file once a second and at once when the reader reports the flow invalid; a changed or deleted file closes reader and initiator (`origin_changed`), and the next check opens the flow again for the same targets (`origin_reopened`). Lab: 50 grains/s again within about a second, no restart, no error.
- No log flood when a connection shuts down. MXL drops a target whose connection shut down (closed by the destination, or after a failed transfer: libfabric's `verbs` provider shuts an endpoint down on a completion error), and with none left every `MakeProgress` logged "No more targets available" (platform: 39,000 lines in 15 minutes; lab: 10,034 in 20 s with the destination stopped). The source now forgets those targets (one `source_connection_lost` line, `errors` + 1, `last_error`). The destination's next request adds the target again, and its target, which listens again after the shutdown, gets a new connection; a later remove no longer meets "Target with id … not found". Lab: 1 line in 20 s, replication back when the destination was.
- `link_down`. Each peer's fabric link is checked on every reconcile pass: the carrier of the local interface that holds `local_fabric_addr` (`/sys/class/net/<netdev>/carrier`), and that some interface holds the address at all ("source interface unavailable", the platform's irdma "Failed to get source interface information"). While it is down the destination drops its target and the source's connection and shows `link_down` with the reason, instead of `target_setup_failed` retries (platform: up to 975 restarts per flow during a 5 h outage of one link). When the link is back it sets up a fresh target and connection. The source's replications to that peer show `link_down` too, and its handshake answer makes the destination wait. One log line per change (`peer_link_down`, `peer_link_up`). `/api/v1/peers` has `link_up`, `link_error` and `fabric_interface`; the web UI shows a down link.
- Metrics: `peer_up{peer,interface}` is 1 only while the peer's control plane answers and the local fabric link to it has carrier (before: control plane only, label `peer`); `peers_up` counts the same. New: `replication_state{flow_id,peer,role,state}` (1 for the current state), `peer_rdma_retransmits_total{peer,device}` (`RetransSegs` of the RDMA device on the fabric interface; irdma only) and `origin_conflicts`.
- Retries of a failed target setup or handshake back off up to 30 s (was 10 s). `target_setup_failed` is logged when the error starts or changes, not on every retry.
- The handshake answer carries the source's state and reason (`state`, `error`). A source in `error` (connected, but no transfer completed for 2 s) makes the destination set its target up again after 1 s without a grain (1, 2, 4, 8 s in a row) instead of 5 s; the destination shows the source's reason in `last_error`.
- Two hosts with the same flow (a function moved to another host and left its domain behind; FlowXer's flow ids are deterministic): the destination replicates from the one whose origin is being written (`live` in the inventory: head index within 5 s of the current time), else one with a writer, and logs `origin_conflict` once per change. Before, the host that had the domain first kept it: the other one marked its own domain `conflict` and did not offer it, so a destination pulled the stale copy at 0 grains/s (platform: vmix 3924b34c on host-02 from host-01). A local domain is no longer `conflict` because a peer holds the same id.
- `fabric_endpoint` (info) logs the libfabric domain of each target and initiator when it is set up (for `verbs` the RDMA device), to compare with `rdma res`. The device in libfabric's "Async event for …" warning is not the one that raised the event: libfabric prints the first device of the fabric.
- `mxl-pattern-writer video … <recreate-after-s>` creates its flow again after that many seconds. `tests/integration/tcp_mesh.sh` checks a re-created flow (45 of 50 grains/s) and a destination that goes away (at most 20 "No more targets" lines in 3 s, then back at 45 grains/s).

## 1.2.3

- Continuous (audio) flows replicate completely. 1.2.2 sent one sync batch per transfer and at most one transfer per pass of the fabric thread (2 ms). With the ST 2110 gateway's batch of 48 samples (1 ms) half of a 48 kHz flow arrived (lab, `tcp` and `verbs`), over `verbs` on the platform's E810 8 % (815 transfers in 10 s, `lag_grains` growing, 89 % zeros for the reader of the mirror). Now one transfer carries every sample written since the last one, up to the target's bounce buffer entry (MXL sizes it from the mirror's sync batch, 10 ms by default), and it starts one pass after the last one completed: over `verbs` MXL's target posts the receive for the next immediate only when its agent drains the last transfer, and a transfer that comes sooner meets "receiver not ready" (soft-RoCE, four audio flows: about 150 per second with 1.2.2, none now). Lab (one host, `tcp` and soft-RoCE, 2 ch 48 kHz, 200 ms history, one and four flows plus 1080p50): 48,000 of 48,000 samples/s on each mirror, none missed, the mirror about 4 ms behind the origin (1.2.2: about 22,500 samples/s, up to 200 ms behind); video unchanged at 50 grains/s; agent CPU unchanged.
- `replication_bytes_total` of a continuous flow counts all channels (it counted 4 bytes per sample: 192 B for a transfer of 48 samples of 2 ch float, which carries 384 B).
- The container workflow runs once per ref; a newer run cancels the older one. The v1.2.2 tag started it twice, and the second run pushed another image over the tag's digest.
- README: keep `RT_PRIORITY` below 50. The kernel's threaded IRQs run at `SCHED_FIFO` 50, and at equal priority a NIC IRQ thread waits for the agent's pass (the platform uses 49).
- `mxl-pattern-writer audio` writes a 2-channel 48 kHz pattern flow in batches of 48 samples, `mxl-pattern-writer samples` counts the correct samples of its mirror; `tests/integration/tcp_mesh.sh` requires 45,000 of 48,000 per second.

## 1.2.2

- `RT_PRIORITY` works for the non-root agent. The binary carries `cap_sys_nice` and `cap_ipc_lock` as permitted file capabilities (`setcap …+p`), and the agent raises them into its effective set at start, before any thread. Kubernetes `capabilities.add` only puts a capability into the bounding set; without an effective `SYS_NICE` the fabric thread got no `SCHED_FIFO` (platform: `rt_priority_failed "Operation not permitted"` on every agent). The effective bit is not set on the file, so a runtime that does not grant `SYS_NICE` still starts the agent (it then logs `rt_priority_failed` as before). The `startup` log line lists the effective capabilities (`capabilities`).
- `deploy/mxl-fabrics-agent.yaml` adds `SYS_NICE` to `capabilities.add`.

## 1.2.1

- A receiver's IS-05 `/active` is read at `<control href>/single/receivers/<id>/active` without a doubled slash. Devices advertise the href with a trailing `/` (nmos-cpp, FlowXer); FlowXer up to 9.16.33 answered the `//single/…` form with 404, so the agent took all its receivers as not routed and replicated none of their flows (small platform: the vision mixer's inputs stayed frozen mirrors, Program rendered no frames).
- A receiver whose `/active` cannot be read is logged once (`nmos_active_unavailable` with URL and HTTP status) until it works again. It counts as not routed, which was silent before.

## 1.2.0

- Transfer pacing is removed again. On the platform's E810 mesh over `verbs` it multiplied retransmissions about 1000-fold and replication broke (517 link restarts in 69 minutes, readers without grains); unpaced, the same links ran at 50 grains/s. MXL's target keeps one receive posted for the immediate data that ends every transfer and posts the next only when the agent reads the completion; with 8 batches per grain the next batch usually arrived before that (receiver not ready). MXL's public API has no transfer without an immediate, so the agent cannot work around it. `TRANSFER_PACING`, `TRANSFER_PACING_SPREAD` and `TRANSFER_PACING_BATCHES` are ignored (a set `TRANSFER_PACING` other than `off` logs `transfer_pacing_removed`); the gauges `transfer_pacing_batches` and `transfer_pacing_spread` are gone.
- Unchanged from 1.1.0: links whose origin writes nothing are not rebuilt (`origin_head`), `lag_grains` is 0 while that head stands still, and `grain_transfer_seconds{provider}` (now transfer to completion of one grain).

## 1.1.0

- Optional transfer pacing: `TRANSFER_PACING=frame` sends each complete video or data grain in `TRANSFER_PACING_BATCHES` slice batches (default 8) whose starts are spread over `TRANSFER_PACING_SPREAD` of the grain duration (default 0.5, 0.1–0.9), instead of one burst at line rate. For receivers whose NIC cannot move bursts from two ports into memory at once (on the platform: E810 at PCIe Gen3 x8 discarding RoCE packets). Uses MXL's slice-range transfer; no MXL change. Adds up to the spread to the latency (10 ms at 50p with the default). Default `off`: nothing changes unless it is set. Restart required.
- `grain_transfer_seconds{provider}` histogram (source grains, first transfer to completion; with pacing the spread included) and the gauges `transfer_pacing_batches` (0 = off) and `transfer_pacing_spread`. The Grafana dashboard shows the p95 transfer time.
- A destination counts a grain in `replication_grains_total` and `replication_bytes_total` once, also when it arrives in several batches.
- A link whose origin writes nothing is no longer rebuilt. 1.0.3 rebuilt a destination without new grains whenever a writer held the origin flow; a decklink input without a signal holds its flow but writes nothing, so its links were rebuilt every 5–40 s (16 times in 15 minutes on the platform) and `replication_restarts_total` rose. The source now returns the origin head index in the handshake answer (`origin_head`), and the destination rebuilds only when the origin moved on after its last grain (or the link is `error`). With a source before 1.1.0 the 1.0.3 rule stays. `lag_grains` is 0 while that origin head stands still (it grew with the TAI index before).

## 1.0.3

- Mirror flows survive an agent restart when `MXL_CLEANUP_ON_EXIT=false`. MXL deletes a flow when its last writer is released or its instance destroyed, so on SIGTERM the agent removed every mirror flow and created it anew at the next start (new inode). Readers on the host stayed on the deleted flow until they were activated again or restarted (platform: mxl-webrtc-monitor, mxl-multiviewer after `kubectl rollout restart`). Now the agent closes its fabric connections and leaves its mirror writers and the MXL instance to the process exit; the next start re-opens the same flows. Lab: restart of the destination agent, the source agent and both, inodes unchanged, a GStreamer reader on a mirror kept reading (before: stopped for good); SIGTERM still exits 143 in about 1 s.
- `lag_grains` (`replication_lag_grains`) is measured on cross-host links. It compared the mirror head with a source head on the same agent, which a destination never has, so it was always 0. Now it is the flow's current TAI index minus the mirror head while a writer holds the origin flow (origin writers commit at the current index); continuous flows count transfer batches. Lab: 1–2 grains on healthy 1080p50 links.
- A source link that is connected but completes no transfer for 2 s is `error` ("no transfer completed for 2 s"). MXL counts a failed transfer (RDMA queue pair out of retries) as never finished, so the initiator stayed `NOT_READY`, sent nothing more and showed `active` with a frozen head. The destination's rebuild (below) replaces the dead connection.
- New mirror `domain_def.json` files carry `description` and `tags` (BCP-007-03 requires them; mxl-st2110-gateway 1.0.2 skipped mirror domains without them). Existing files are not rewritten.
- A dead link is set up again. A destination without a new grain for 5 s while it is in `error` or its source flow is being written (a peer that hung, a queue pair out of retries, a closed connection that reports nothing) tears its target down and repeats the handshake; the source replaces the dead connection with the new target. `restarts` counts it, the log says `replication_restarted`. The wait doubles with each rebuild in a row (5, 10, 20, 40 s). Before, such a link stayed `error` (or even `active` without grains) with `restarts` 0 until the agent restarted.
- `last_error` is cleared when a link works again: a source or destination pass without a new error is `active` again (a destination in `error` also needs new grains), and a successful handshake clears `recv` or `http …`. The `errors` count keeps the history.
- `/metrics` exports `replication_grains_total`, `replication_bytes_total` and `replication_errors_total` per flow, peer and role, and `replication_restarts_total` per destination. Before, `replication_grains_total` was always 0 and the other three were missing. `replication_errors_total` has no `kind` label (SPEC §12 now says so; the Grafana error panel groups by flow and role); the histograms `grain_transfer_seconds` and `setup_seconds` and `nmos_poll_errors_total` are marked "not implemented yet".

## 1.0.2

- The image contains `ibverbs-providers`, the user-space RDMA drivers (`irdma` for Intel E810, `mlx5` for ConnectX, `rxe`) and `/etc/libibverbs.d`. Without them libibverbs found no device even with `/dev/infiniband` mapped, and an agent with `DEFAULT_PROVIDER=verbs` exited with `no_fabric_provider`. `ibverbs-utils` adds `ibv_devices` and `ibv_devinfo` to check what the container sees. Lab check over soft-RoCE (`rxe` on one host, two agents): 4 flows of 1080p50 replicate over `verbs` at 50.2 grains/s, lag 0, no errors.
- A connected source link stays `active`. `mxlFabricsInitiatorMakeProgressNonBlocking` returns `MXL_ERR_NOT_READY` while transfers are still in flight, which on `verbs` is most passes; the agent showed `pending` for those, and the destination copied it, so links that moved 50 grains/s flipped between `active` and `pending` in `/api/v1/replications` and the web UI (on `tcp` too, less often). Only a link that has not connected to its current target is `pending`. The `replications_active` metric counted both states and does not change.

## 1.0.0

Stable platform contract. A later breaking change needs v2.

New settings, with the previous names kept as aliases:

- `MXL_DOMAIN_SCAN_PATH` is the MXL parent directory. `MXL_ROOT` is the alias. Default remains `/Volumes/mxl`.
- `MXL_CLEANUP_ON_EXIT` removes this agent's own mirror directories on shutdown. `CLEANUP_MIRRORS_ON_EXIT` is the alias. Default remains false.
- `NMOS_SEED` sets the UUIDv5 node id. Unset, the id is still UUIDv5 of `HOST_ID`.
- `NMOS_LABEL` sets the node label. Default is `HOST_ID`.
- `NMOS_TAGS` adds a JSON object of tags to the node. The host-id tag is still set.
- `NMOS_DNS_SD` defaults to **false**. DNS-SD browse and mDNS advertisement are both off unless this is `true`. A deployment that relied on an empty `NMOS_REGISTRY_ADDRESS` to browse must set `NMOS_DNS_SD=true`.
- `NMOS_HOST_ADDRESS` is the IP literal announced in the node href, `api.endpoints[].host`, and the service href. Unset, the first non-loopback IPv4 is used. `HOST_ID` remains the fabrics peer id.
- `NMOS_QUERY_PORT`, when unset, is `NMOS_REGISTRY_PORT + 1` rather than a fixed 3211.
- `STATE_DIR` (default `/config`) is where the process stores its configuration file.
- `SHUTDOWN_TIMEOUT_S` (default 10) is the SIGTERM budget.

Behaviour:

- SIGTERM and SIGINT exit **143** after MXL resources are released, the node is removed from the registry, and own mirrors are deleted when cleanup is on.
- A listen port that cannot be bound exits **75**.
- `/readyz` is 200 only when the scanner is running and, if a registry is configured, the node is registered.
- `GET /api/v1/config/export` and `POST /api/v1/config/import` save and restore configuration. This agent has no secret settings.
- An existing mirror `domain_def.json` with a different id is not overwritten.
- The image is uid 1000. `IPC_LOCK` is for RDMA registration. OCI label `io.dmf.mxl.revision` is the MXL commit `218ddaa0a08c12ffe75fc475ae65aa3d9eef16d7`. Version tags `X.Y.Z`, `X.Y`, and `X` are not moved. `nightly-dev` remains the moving tag on `main`.
