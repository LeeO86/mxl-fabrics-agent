# mxl-fabrics-agent — Implementation Plan

This document records how `SPECIFICATION.md` (draft v0.1) is implemented, including
places where the real MXL 1.1 Fabrics API differs from the spec's paraphrase.

## 1. Pins

| Component | Pin |
| --- | --- |
| MXL | `dmf-mxl/mxl` `release/v1.1` at `218ddaa0a08c12ffe75fc475ae65aa3d9eef16d7` (includes the `validSlices` reset, issue 717) |
| libfabric | `v2.3.1` in the image (`FI_SOCKADDR_IP` / tcp). Any libfabric ≥ 2.3 with the `tcp` and `verbs` providers is acceptable |
| nmos-cpp | `fe303849527394b03bdedc8f161f377fe458bb62` (same commit as mxl-decklink) |
| Provider hardware | `verbs` via libibverbs. Intel E810 uses the `irdma` kernel provider. NVIDIA/Mellanox ConnectX uses `mlx5`. Both are the same Fabrics provider (`verbs`) |

The endpoint-id collision fix and the configurable target completion-queue depth (`cqDepth`) are in this MXL pin. The separate batch call `mxlFabricsTargetReadGrainsNonBlocking` was not merged. Targets drain with a tight loop of `mxlFabricsTargetReadGrainNonBlocking`, then commit.

## 2. Deviations

1. **One fabrics instance per MXL domain, not per provider.** `mxlCreateInstance` takes one domain directory and `mxlFabricsCreateInstance` wraps that instance. Provider (`verbs` or `tcp`) is chosen per target or initiator. Calls for one domain run on that domain's thread.
2. **One initiator per (origin flow, local fabric address).** A single initiator binds one address. On a switched network that is one initiator per flow. On a direct-link mesh, a flow sent to two peers on two NICs uses two readers and two initiators.
3. **Include and exclude filters are separate.** `MIRROR_INCLUDE_DOMAINS`, `MIRROR_INCLUDE_FLOWS`, `MIRROR_EXCLUDE_DOMAINS`, `MIRROR_EXCLUDE_FLOWS`. An empty include list does not filter. The combined `MIRROR_INCLUDE` / `MIRROR_EXCLUDE` keys are rejected because domain ids and flow ids are both UUIDs.
4. **`/api/v1/info` includes `boot_id`.** A new UUID per process. Destinations repeat the handshake when it changes or when the peer inventory revision goes backwards.
5. **Repeated `POST /replications` replaces `target_info`** for the same `(flow_id, dest_host_id)` and returns the existing `replication_id`.
6. **`WEB_ENABLE=false` hides the UI and config writes.** `/api/v1` stays up so peers still work. Health and metrics stay up.
7. **`METRICS_PER_FLOW` defaults to true.**
8. **Grain commit snapshots metadata first.** On this MXL revision `mxlFlowWriterOpenGrain` clears `validSlices` and the invalid flag. The agent reads `mxlFlowWriterGetGrainInfo` before opening and commits that snapshot, so the index, flags, and slice count written by Fabrics are preserved.
9. **`on-demand` is implemented.** mxl-decklink and mxl-st2110-gateway reject an IS-05 activation whose domain is not already on disk, so those receivers need `MIRROR_MODE=eager` (the default). `on-demand` is for readers that retry domain discovery.
10. **Query observation is polled** every `NMOS_POLL_INTERVAL_MS` (and on the reconcile loop). Correctness does not depend on a single websocket event. The agent's own Node is a real nmos-cpp node and still serves its HTTP and websocket listeners.
11. **Test connect** (`POST /api/v1/peers/{id}/test`) checks the peer control plane and sets up a local fabrics target on the configured provider and address. It removes that target before returning.
12. **Metrics (spec §12) are partly implemented.** `replication_errors_total` has no `kind` label: the fabric pass counts errors and keeps the last message, it does not classify them. `setup_seconds` and `nmos_poll_errors_total` are not implemented (1.0.3); `grain_transfer_seconds` is since 1.1.0.
13. **Dead links are detected by missing grains, not by a fabric error.** A closed `tcp` connection or a hung peer often reports nothing to the initiator or the target. MXL's RC initiator (at the pin) only logs a completion error: the failed transfer stays pending, `mxlFabricsInitiatorMakeProgressNonBlocking` returns `NOT_READY` forever and the agent sends nothing more. The destination rebuilds its target when no grain arrived for 5 s while the link is in `error` or the origin head moved after its last grain (the source returns `origin_head` in the handshake answer since 1.1.0; 1.0.3 used the writer lock from the peer inventory, and a decklink input without a signal, which holds its flow but writes nothing, was rebuilt every 5–40 s on the platform); the wait doubles per rebuild in a row up to 40 s. The source marks a link connected but without a completed transfer for 2 s as `error`. One initiator serves all destinations of a flow, so a dead destination blocks the others until it is rebuilt (1.0.3). Since 1.3.0 the source returns its state and reason in the handshake answer, and a source `error` makes the destination rebuild after 1 s without a grain (`shouldRebuild` in `src/replication/policy.cpp`).
18. **A connection that shuts down is forgotten at the source (1.3.0).** Over `verbs` libfabric turns a completion error into `FI_SHUTDOWN` on the endpoint (`vrb_poll_cq` → `vrb_shutdown_ep`, libfabric 2.3.1); MXL's `RCInitiatorEndpoint` takes `FI_SHUTDOWN` in `Connected` as "Remote endpoint has closed the connection", flushes, and evicts the endpoint. The same happens when the destination closes it. With no endpoint left `RCInitiator::makeProgress` throws "No more targets available" (`MXL_ERR_INTERRUPTED`), and 1.2.3 called it on every pass (platform: 39,000 lines in 15 minutes; a later `RemoveTarget` threw "Target with id … not found"). The agent cannot see a single evicted target, only none left: it then frees its target infos and keeps the initiator and reader. The destination repeats its `POST /replications` every pass and the target is added again; MXL's `RCTarget` goes back to listening after a shutdown, so the same target info connects again. libfabric's "Async event for <device>" names `fab->info`, the fabric's first device (`vrb_fabric`, `vrb_eq_process_async_events`), not the device whose queue pair failed; libfabric already restricts the `fi_getinfo(node, FI_SOURCE)` answer that MXL's `selectSourceInterface` takes to the device the address binds to (`vrb_handle_sock_addr` → `vrb_del_info_not_belong_to_dev`), so PD, MRs, CQ and QP are on one device. `fabric_endpoint` logs that device (the interface list's `fi_domain_name`) per target and initiator.
19. **Re-created origin flows (1.3.0).** MXL deletes a flow with its last writer; a writer that restarts creates it with a new inode, and a reader sees `MXL_ERR_FLOW_INVALID` only on a too-early read after that. MXL's public API has no inode, so the source stats `<domain>/<flow>.mxl-flow/data` before it opens the reader and again once a second, and also acts on `FLOW_INVALID`. A changed or deleted file closes reader and initiator (the destinations' targets see the connection close and listen again); the check one second later opens the new flow and adds the same targets. A flow that appears after the agent started needed nothing new: the source opens its reader when the destination asks, and the destination asks once the flow is in the source's inventory (lab 2026-10-09, `late`).
20. **Fabric link state per peer (1.3.0).** No relay over a third host (user decision). The controller checks each peer's local fabric address on every pass: `getifaddrs` for the interface that holds it, `/sys/class/net/<netdev>/carrier`, and the interface's RDMA device (`/sys/class/net/<netdev>/device/infiniband/`) with its `ports/1/hw_counters/RetransSegs` (irdma). A destination with a dead link drops its target and `DELETE`s it at the source once, shows `link_down`, and sets up fresh ones when the link is back; source rows to that peer show `link_down`. `peer_up` is the control plane and the link together, with an `interface` label, so the platform's alert on `peer_up == 0` covers both.
21. **One origin per flow when several hosts hold it (1.3.0).** Up to 1.2.3 a local domain whose id a peer also exported was classified `conflict` and not exported, so the host that had it first kept it, even with a stale flow (platform: FlowXer moved from host-01 to host-03; its deterministic flow ids stayed on host-01 with a frozen head and a writer lock, and host-02 replicated 0 grains/s from there). Now every local domain is exported with `live` per flow (the head index from the flow's data file, offset 200, within 5 s of `CLOCK_TAI` at the flow's rate), and the destination chooses per flow (`chooseOrigin`): live, then writer, then the current choice, then the lowest `host_id`.
22. **Origin gaps are passed over (1.3.1).** MXL 218ddaa's discrete writer, when it opens an index more than one after its last complete grain, marks the skipped slots (at most a ring) invalid with no valid slice and their own index (`PosixDiscreteFlowWriter::openGrain`); its reader returns such a slot as OK with `MXL_GRAIN_FLAG_INVALID` (`getGrainImpl` does not compare the slot's index). Up to 1.3.0 the source sent it as an empty grain (`TransferGrain(index, 0, 0)`: the grain header and an immediate), which the destination committed as an invalid grain, so over `tcp` gaps cost nothing (lab: 1663 transfers for 1157 written grains in 30 s, no error). Over `verbs` each one is another immediate on MXL's single posted receive (deviation 16), sent in the first pass after the last transfer completed, back to back with the next grain. The platform's replay outputs (gaps when the playout is more than 2 grains late) rebuilt 2–3 times in 30 s at 21.5 and about 0 grains/s while FlowXer (late, no gaps) ran at 50.5 on the same path; soft-RoCE counted 3–6 "receiver not ready" per 30 s with 1.3.0 and none with 1.3.1. `originGap` (`src/replication/policy.cpp`) skips, while the head is later, an index whose slot is invalid with no valid slice, holds another index (a writer that opened the flow again leaves older grains; the destination then read the old index from the header and failed with `open grain 8`), or is not complete. The head grain is always sent, also when invalid. The destination's mirror writer marks the skipped indexes invalid when it opens the next grain, as on the origin. Not changed: `TOO_LATE` still jumps to the current TAI index.
23. **The `verbs` address list is built again when it lacks a held address (1.3.1).** libfabric 2.3.1's `vrb_getinfo` runs `vrb_init_info` once (`init_done`): it lists the RDMA devices, their addresses (`vrb_getifaddrs` → `vrb_devs`) and `FI_EP_MSG` infos only for devices with an address (`vrb_device_has_ipoib_addr`) into `vrb_util_prov.info`. MXL's `mxlFabricsGetInterfaces` calls `fi_getinfo` without node or hints; verbs then binds `localhost`, finds no device and takes the source addresses from `vrb_devs` (`vrb_fill_addr` → `vrb_get_srcaddr_devs`). The agent's first `fi_getinfo` is `probeFabrics` at start, so an address missing then stays missing (`pickInterface`: "provider verbs has no interface for …"). `fi_getinfo` with `FI_RESCAN` (`rdma/fabric.h`, libfabric ≥ 2.2) builds both lists into temporaries and swaps them under `vrb_info_mutex`; every other user of `vrb_util_prov.info` takes that lock (`vrb_fabric`, `vrb_check_verbs_info`, `vrb_eq`, `ofi_prov_check_info`) and an open fabric keeps its own `fi_dupinfo`, so running replications are not touched. `pickInterface` rescans once and asks again when it has no interface for an address that `fabricLink` finds on an interface with carrier (`rescanDue`), at most once per 5 s per process. A self-restart (the fallback considered) is not needed. The address check itself is 1.3.0's link state (deviation 20): an address that is gone is `link_down`, back is `link_up`. A source whose own link to the destination is down now answers `link_down` without setting anything up; before, without the address, `ensureInitiator` failed on every request and the destination showed `http 500`.
14. **Lag is measured against TAI, not the source's reported head.** The destination never sees the origin head; origin writers commit at the current TAI index, so the lag is `mxlGetCurrentIndex(rate) − mirror head` while a writer holds the origin flow (1.0.3).
15. **Mirror writers are not released on SIGTERM without cleanup.** MXL deletes a flow when its last writer is released (`Instance::releaseWriter`) or its instance destroyed. With `MXL_CLEANUP_ON_EXIT=false` the agent leaves writers and instance to the process exit, so the flows and their inodes survive and readers keep them (1.0.3).
16. **Transfer pacing is an agent setting, not an MXL change (1.1.0, user decision 2026-10-06).** The platform's small cluster has Intel E810-XXV cards at PCIe Gen3 x8 (the CPUs have Gen3 only): about 6.5 GB/s of DMA for two 25G ports. Grains sent as one 5.5 MB burst at line rate on both ports at once overrun the receiving RDMA engine although PFC is in effect (`ip4InDiscards` on the receiver equal `RetransSegs` on the sender), and now and then a queue pair runs out of retries. ice offers no rate limit for RDMA queue pairs (no `dcb maxrate`, no devlink rates, mqprio shapes LAN queues only). `TRANSFER_PACING=frame` (default `off`) sends a complete grain in `TRANSFER_PACING_BATCHES` slice batches whose starts are spread over `TRANSFER_PACING_SPREAD` of the grain duration, through MXL's public slice-range transfer (`mxlFabricsInitiatorTransferGrain(index, start, end)`); MXL stays upstream. The destination takes the grain index from the header in the first batch, so the source starts a grain again from slice 0 after a target change or a pause of more than 100 ms. The fabric thread sleeps until the next batch is due instead of 2 ms. Options considered: a separate image (a second artifact for the same code) and a NIC rate cap (not available). The platform turns it on for the small cluster only. **Removed in 1.2.0 (user decision 2026-10-06):** on the platform's E810 mesh over `verbs` (spread 0.5, 8 batches, 69 min) retransmissions rose about 1000-fold (RetransSegs 1–4 M per port against 10–25 k in six unpaced hours), `ip4InDiscards` per packet about 60-fold, 517 link restarts on one host, and readers on other nodes got no grains. Cause in MXL 218ddaa: `RMAGrainIngressProtocol` posts one receive for the immediate data (`start()`) and the next only when the agent drains the completion (`read()`), while `RMAGrainEgressProtocol` ends every slice-range write with an immediate; with 8 per grain the next one usually arrived before the receive was posted again (receiver not ready, retries, queue pairs out of retries). The public API has no transfer without an immediate, and waiting for the initiator's completion does not help (it only means the HCA consumed the receive). `tcp` has no receive per immediate, so the lab and CI did not show it. `TRANSFER_PACING` is ignored with a warning (`transfer_pacing_removed`); the idle-origin fix, `origin_head` and `grain_transfer_seconds` stay.
17. **Continuous flows: one transfer per pass and completion, with all new samples (1.2.3).** Up to 1.2.2 a source sent the origin's sync batch (`maxSyncBatchSizeHint`) per transfer, and only in a pass where `mxlFabricsInitiatorMakeProgressNonBlocking` returned OK, so at most one per 2 ms pass. The ST 2110 gateway writes audio with a hint of 48 (1 ms at 48 kHz): half of the samples arrived over `tcp` and soft-RoCE, 8 % over `verbs` on the platform's E810 (the lab tests used the test player, whose hint is 480). Over `verbs` the same limit as in deviation 16 applies: `RMASampleIngressProtocol` posts one receive for the immediate data and the next only when the agent drains the completion, which the destination does once per pass; a transfer that arrives before meets "receiver not ready" (soft-RoCE: 30–150 per second with 1.2.2; E810 pays a retry timer for each). Now a transfer carries every sample since the last one, limited by the targets' bounce buffer entry (`bounceBufferInfo.entrySize` in the target info, minus MXL's 16-byte `AudioEntryHeader`; without it the origin's sync batch), and starts no earlier than one pass (`kPassInterval`, 2 ms) after the pass that saw the last one complete. That is about 250 transfers per second of about 4 ms each. Without the extra pass (every pass, about 490 per second) soft-RoCE still counted 4–20 "receiver not ready" per second; with it none. The entry holds the mirror's sync batch, which MXL sets to 10 ms for the agent's writer (no options), so a link keeps up while a transfer takes less than 10 ms. Other options: a receive thread per target blocking in `mxlFabricsTargetReadSamples` (a second thread on MXL objects that the fabric thread serialises), a larger sync batch on the mirror writer (readers of the mirror would wake less often).

## 3. Process

One thread reconciles scanner, peer, and NMOS snapshots into mirror plans (`src/mirror/lifecycle.cpp`) and pull requests. Each MXL domain that the agent opens has a fabric thread that serialises MXL and Fabrics calls, drains target completion queues, and transfers new grains or samples. Peer inventory polling and the NMOS observer run on their own threads. The HTTP server is another thread.

`verbs` setup failure with `PROVIDER_FALLBACK=tcp` retries that link on `tcp` and reports `fallback: true`.

## 4. Local nodes on the pod network

`LOCAL_NODE_CIDRS` (empty by default, not a runtime key) adds a fourth local-node
rule after the host-address, hostname, and static-list rules, and after the
agent's own Node is excluded. An endpoint host that is an IP literal is matched
directly. A DNS name is resolved with `getaddrinfo` only when the list is
non-empty, with a 250 ms bound and a 30 s positive and negative cache. A name
that does not resolve is not local and is logged once at debug. The match rule
(`list`, `hostname`, `ip`, `cidr`) is logged at debug as `nmos_node_local`.

The platform renders each node's pod CIDR into that agent's config. The agent
does not watch the Kubernetes API or derive the CIDR from routes. A later
`LOCAL_NODE_CIDRS=auto` could do that.
